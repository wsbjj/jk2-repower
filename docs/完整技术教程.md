# JK-2 完整技术教程

> 本文保留原有协议与抓包记录，部分为特定环境下的历史观察。安装、默认地址与使用步骤请以 [项目首页](../README.md) 为准。操作只限有权使用的设备。

## 1. 原理总览：三条通道和它们的边界

先把链路画清楚，后面每一节都是这张图里的一个格子。

```
┌──────────┐   ① 扫码    ┌──────────────────┐   ② HTTPS    ┌─────────────────────┐
│  设备侧面 │ ──────────> │ 微信小程序         │ ──────────> │ ThingsBoard 云端      │
│  二维码    │             │ （Chaos VM 混淆）  │ <────────── │ /api/v1/{token}/... │
└──────────┘             └────────┬─────────┘              └──────────┬──────────┘
                                  │ ③ BLE（真正下发指令的通道）         │ ④ 配置/遥测
                                  v                                     │
                         ┌──────────────────┐  attributes / telemetry   │
                         │ 高卫监控器         │ <─────────────────────────┘
                         │ ffe0 / ffe1      │
                         └──────────────────┘
```

三个执行通道，能力完全不同：

| 通道 | 能做什么 | 不能做什么 | 本仓库入口 |
|---|---|---|---|
| **云端设备令牌** `/api/v1/{token}/...` | 读全部属性、读 RPC 字符串、读遥测 | 写 `shared` 属性（服务端只允许 client scope） | `curl` / `./run.sh dev-state` |
| **云端账号 JWT** `/api/auth/login` | 读 + **写** `SHARED_SCOPE`（真正能远程控电） | 需要账号密码；部分学校锁定策略会覆盖写回 | `client/tb.mjs` |
| **本地 BLE** `ffe0/ffe1` | 写配置串 + 加密 RPC → **设备真的执行** | 必须人在 10 米内；Mac/树莓派要在宿舍 | `ble/jk2.py` |

三个关键结论（都是实测，不是推测）：

1. **控制只能走 BLE**（或账号 JWT 的 `SHARED_SCOPE` 写入）。设备令牌只能读。
2. **设备是纯 BLE，没有 WiFi/4G**。云端只能存配置，指令必须有人（Mac / 树莓派）在跟前发。
3. **写设备要节制**。这台设备的正常负载是「人走到跟前扫一次码」，高频写入可能把它写进故障态（见 [第 19 节](#19-写入预算与故障码-24)）。

### 2.1 依赖

| 组件 | 版本 | 用途 | 装法 |

一键装：

```bash
bash scripts/setup.sh          # 项目自带的依赖安装脚本
python3 -c "import bleak; print('bleak', bleak.__version__)"
node -v && mitmdump --version
```

自测通过仅说明本地模拟流程通过；真实服务、设备、权限和网络仍需分别验证。

### 2.4 三份配置各自管什么

| 文件 | 内容 | 谁读它 |
|---|---|---|
| `private/local.env` | 真实域名 `JK2_BASE`、设备令牌 `DEV_TOKEN`、`JK2_APPID` | `run.sh`、各 `.command`（自动 source） |

## 5. 抓包 I：HTTPS 流量（mitmproxy）

### 5.1 原理

小程序走 HTTPS。中间人抓包要满足三件事：

1. 手机把流量指向你的代理（WiFi 代理设置）；
2. 手机信任你的 CA（装 `mitmproxy` 根证书并在「证书信任设置」里打开开关）；
3. 目标 App 不做证书固定（Pinning）。前两条是配置问题，第三条是逆向问题（见 [第 7 节](#7-抓包-iiissl-pinning-与-frida-绕过)）。

### 5.2 一键启动

```bash
./run.sh capture           # 等价 bash scripts/capture.sh 8080
```

脚本会打印本机局域网 IP 和手机端要做的 5 步。手动版：

```bash
mitmdump -s capture/mitm_addon.py --set dump_dir="$PWD/private/captures" -p 8080 --set block_global=false
```

### 5.3 手机侧（照着做，别跳）

1. iPhone 与 Mac 连**同一个 WiFi**（不能一个 5G 一个 2.4G 走不同网段）。
2. WiFi → 当前网络 → 配置代理 → 手动：服务器填 Mac 的 `ipconfig getifaddr en0`，端口 `8080`。
3. Safari 打开 `http://mitm.it` → 下载 Apple 证书 → 允许 → 安装描述文件。
4. 设置 → 通用 → 关于本机 → **证书信任设置** → 打开 `mitmproxy` 开关。
   > 这一步不做，抓到的全是 `CONNECT` 隧道和证书错误，是最常见的「抓不到」原因。
5. 打开微信 → 目标小程序 → **完整走一次你要抓的动作**（比如：扫码 → 点复电）。

### 5.4 插件产物

`capture/mitm_addon.py` 会把流量落成三类文件：

| 文件 | 内容 |
|---|---|
| `private/captures/<时间>.jsonl` | 每条请求一行：method / url / headers / body |
| `private/captures/summary.json` | 聚合后的接口清单 + 提取出的凭证 + 推断的签名模板 |
| `private/captures/suggested-config.json` | 可直接当 `private/config/config.json` 的初稿 |

插件只对「像业务接口」的路径做聚合（正则 `/api/|/dorm|/power|/recover|/electric|/room|/auth|/login|/scan|/qr|/order`），
避免被微信埋点（`report-online.sh.wxgateway.com`）和 CDN 淹掉。

### 5.5 抓不到「写」请求怎么办

这是本项目的经典坑，两次抓包都只抓到读，没抓到写：

```
rpc        getCurrentRPCStr         → 明文配置串
rpc        getCurrentRPCStr_B03.08  → 密文 IV:CT
telemetry  26 个字段
（没有 control / recover / write）
```

原因不是抓包失败，而是**这个动作根本不走 HTTP**——它走 BLE。
判据：埋点里能看到页面跳转 `pages/thingsboard_B03?bt_id=...`，但没有任何写请求。
此时正确动作是转 [第 8 节 蓝牙抓包](#8-蓝牙抓包-i怎么把空口流量录下来)，不要继续在 HTTPS 里挖。

### 5.6 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| 手机连不上网 | 代理 IP/端口错，或 Mac 防火墙拦了 | 换 `en1`、临时关防火墙 |
| Safari 打开 mitm.it 提示不信任 | 只装了描述文件，没开「证书信任」 | 设置 → 通用 → 关于本机 → 证书信任设置 |
| 小程序白屏 / 报网络错误 | 证书固定（Pinning） | 走 [第 7 节](#7-抓包-iiissl-pinning-与-frida-绕过) |
| 抓到一堆乱码 body | gzip/br 压缩或二进制 | 用 `mitmproxy` 的 Flow 界面看，或 `--set http2=false` |
| 只抓到 CONNECT | 没装 CA 或没信任 | 重做 5.3 的 3、4 步 |

## 6. 抓包 II：HAR 文件的解析与判读

有时候你手上不是实时抓包，而是别人/别的工具给你的 `.har`（ProxyPin、Charles、Chrome DevTools 都能导出）。
本项目带一个专门的分析器。

### 6.1 跑

```bash
node scripts/har_analyze.mjs private/captures/xxx.har                # 默认输出到 private/analysis/
node scripts/har_analyze.mjs private/captures/xxx.har --out private/analysis2
```

### 6.2 它做什么

1. 按 host 分组、还原时间线；
2. **认领人**：解 `wxgateway` 埋点的 base64，拿出 appid / 版本 / 页面路径；
3. **认领设备 API**：`/api/v1/{token}/telemetry|rpc|attributes` → 抽 token、方法名、参数；
4. `telemetry` 的数字 key 展开成 `k=v` 表；
5. `rpc` 响应分两种形态处理：
   - 明文 `"D1:2026,34:11,...,D13:Y"` → 解析成 `{寄存器: 值}`；
   - 密文 `"BASE64IV:BASE64CT"` → 算分组长度/熵，判断是不是 AES/SM4 类分组密码；
6. 产出 `suggested-config.json` + `har-analysis.json`。

### 6.3 判读要点

- **看 host 分布**。业务域名 + 埋点域名 + CDN 域名三者的比例能直接告诉你「这个 App 到底连不连服务器」。
- **看有没有 `POST` 到业务域名**。只有 `GET attributes` / `POST rpc` / `POST telemetry` 说明是纯读；
  出现 `SHARED_SCOPE`、`recover`、`control` 才是写。
- **HAR 里的 body 是 latin-1 存的二进制**。ProxyPin 的情况要用 `body.encode('latin-1')` 才能 1:1 还原，
  直接 `utf-8` 会出现 U+FFFD。
- **埋点里能捡到金子**：页面跳转事件里带着 query，例如 `pages/thingsboard_B03/thingsboard.html?bt_id=B03-XXXX`
  ——**二维码内容就是设备令牌本身**，这条信息比抓包本身更值钱。

### 6.4 完整性核查（HAR 是否可信）

写结论前先核这几项，否则容易把「抓包截断」误判成「客户端没发」：

| 检查 | 方法 |
|---|---|
| JSON 可解析 | `jq '.log.entries | length' x.har` |
| body 是否截断 | 逐条比对 `Content-Length` 与 body 字节数 |
| 时间戳连续性 | 看最早/最晚 `startedDateTime` 是否有断档 |
| 二进制是否被破坏 | 搜 `\uFFFD`；ProxyPin 用 latin-1 |
| 分片覆盖率 | CDN 分片只抓到一部分时，别急着说「包不全」 |

## 7. 抓包 III：SSL Pinning 与 frida 绕过

只有当「代理配好了、证书信任了，但小程序仍然白屏/报错」时才需要这一节。

### 7.1 判断是不是 Pinning

- 浏览器能访问 `https://mitm.it`，说明代理和 CA 正常；
- 但小程序内所有请求失败、或 `mitmproxy` 里只看到 `CONNECT` 后立刻断开 → 大概率 Pinning。

### 7.2 前置：越狱 + frida-server

iPhone SE（第一代，`iPhone8,4`）最高 iOS 15，`palera1n` 支持，是这条路最省事的机型。

```bash
# 1) 装 frida-server（越狱后 Sileo/Cydia 加源 https://build.frida.re）
# 2) Mac 侧
pip install frida-tools
frida-ps -U | grep -i -E "wechat|微信"       # 确认能看到进程
```

### 7.3 两种注入方式

```bash
# A. spawn（启动即注入，推荐：Pinning 校验在启动早期就装了）
frida -U -f com.tencent.xin -l capture/frida_unpin.js --no-pause

# B. attach（进程已经在跑）
frida -U WeChat -l capture/frida_unpin.js
```

`capture/frida_unpin.js` 做的是：Hook `NSURLSession` 的 `didReceiveChallenge` 系列回调、
`NSURLConnection` 的证书校验、以及常见的 `SecTrustEvaluate` 路径，让 mitmproxy 的 CA 被接受。

### 7.4 验证

注入后 frida 控制台会出现 `[unpin]` 前缀日志；此时再看 `mitmproxy`，之前失败的请求应该变成正常 200。

### 7.5 如果还是不行

- 有些版本把校验做在 native 层（`BoringSSL`），要 hook `SSL_CTX_set_verify` 之类的 C 函数；
- 更省事的替代：**不走 Pinning 这条路**，改用 [第 11 节](#11-小程序逆向-i定位包解密解包) 直接从本机微信缓存里拿包——
  缓存里的 `wxapkg` 不需要任何证书。

> 经验：本项目最终**没有依赖越狱**。抓包 + 解包 + 蓝牙空口抓包三条证据链交叉验证，比硬刚 Pinning 更快。

## 8. 蓝牙抓包 I：怎么把空口流量录下来

### 8.1 为什么非要抓空口

因为**真正下发指令的那条链路根本不经过 HTTP**。HTTPS 抓包只能看到「读配置」，看不到「写指令」：

```
rpc  getCurrentRPCStr        ← 读明文配置串
rpc  getCurrentRPCStr_B03.08 ← 读加密 RPC
telemetry                    ← 上报读数
（没有 write）
```

而 ATT 层上写的是：配置串 + 加密 RPC，全部通过 `ffe1` 写进设备。

> 一个容易误解的点：**BLE 链路层加密不影响 HCI 日志的可读性**。
> 手机侧 HCI log 记录的是主机↔控制器之间的数据，加密发生在控制器内部（LL 层）。
> 所以你看到的是**明文 ATT PDU**，不需要 LTK。

### 8.2 方案对比（按省事程度排序）

| 方案 | 平台 | 能拿到什么 | 成本 |
|---|---|---|---|
| **iOS HCI 日志 + PacketLogger** | iPhone | 完整 HCI/ATT，含 handle 与 payload | 免费，要开发者模式 |
| **Android HCI snoop log** | Android | 同上，`btsnoop_hci.log` | 免费，开发者选项 |
| **macOS 蓝牙日志** | Mac | Mac 作为中心时的 ATT 交互 | 免费 |
| **nRF Sniffer + Wireshark** | 任意 + 硬件 | 空中包（含广播、连接、加密前握手） | 需一块 nRF52840 dongle |
| **Sniffle + CC26xx/CC1352** | 任意 + 硬件 | 更细的链路层（含 CONNECT_IND、加密启动） | 需 TI 板 |
| Ubertooth | 任意 + 硬件 | 老方案，BLE 支持一般 | 不推荐 |

**推荐：iOS 日志 + PacketLogger**。理由：手机就是真实客户端，抓到的就是你实际会重放的流程。

### 8.3 iOS：开发者模式 + 蓝牙日志 + PacketLogger

1. iPhone：设置 → 隐私与安全性 → **开发者模式** → 打开 → 重启 → 确认。
2. iPhone：设置 → 开发者 → **蓝牙调试日志（Bluetooth logging）** → 打开。
   （部分版本在「设置 → 开发者 → Logging → Enable Bluetooth logging」）
3. Mac 安装 Xcode，然后：
   Xcode → Open Developer Tool → More Developer Tools… → 下载 **Additional Tools for Xcode** → 里面是 `PacketLogger.app`。
4. USB 连上 iPhone，打开 PacketLogger，左上角设备选你的 iPhone → **Start**。
5. 手机上完整走一次要抓的动作：
   ```
   打开微信 → 小程序 → 扫码 → 进设备页 → 点「复电」→ 等 3~5 秒
   ```
6. PacketLogger 点 **Stop** → `File → Save As…` → 存成 `xxx.pklg`。
7. 拷进项目：
   ```bash
   cp ~/Downloads/xxx.pklg private/captures/jk-2蓝牙包.pklg
   ```

> 抓完记得把「蓝牙调试日志」关掉：它会持续写盘，且对续航有影响。

### 8.4 macOS / Linux / Android

```bash
# macOS：PacketLogger 选 "Mac" 作为设备（抓本机 CoreBluetooth 的 HCI）
# Linux：内核自带 btmon，直接录
sudo btmon -w private/captures/cap.btsnoop
sudo hcitool lescan --duplicates        # 另一个终端，触发扫描

# Android：开发者选项 → 启用蓝牙 HCI 监听日志 → 复现操作 → 取日志
adb pull /sdcard/btsnoop_hci.log private/captures/android.btsnoop
adb bugreport .                          # 部分机型日志在 bugreport 里
```

### 8.5 硬件嗅探（需要能抓「加密前」的握手时）

```bash
# nRF Sniffer：装 nRF Connect + Wireshark 插件，选板子 → 抓到 .pcapng
# 关键过滤
tshark -r sniff.pcapng -Y "btle" -V | less
```

## 9. 蓝牙抓包 II：自己解析 pklg（PacketLogger）格式

PacketLogger 的格式**没有公开文档**，网上能搜到的解析器大多只能解出第一条。这里写清楚。

### 9.1 记录结构（实测版）

```
┌────────────────┬──────────────────────────┬───────────────────────────────┐
│ 4 字节 totalLen │ 8 字节 时间戳              │ totalLen - 8 字节 payload      │
└────────────────┴──────────────────────────┴───────────────────────────────┘
      ↑ 不含自身 4 字节 → 整条记录占 4 + totalLen 字节
```

- `totalLen` **包含** 8 字节时间戳，但**不包含**它自己那 4 字节；
- 时间戳看起来是 `int32 LE 秒 + int32 LE 小数位（量级像微秒）`。
  **它的绝对基准还没完全对上**：按 Unix 秒解释会比文件日期早约 4 周，按 CFAbsoluteTime 解释会晚到 2057 年，
  所以脚本里用**相对首条的偏移**输出（判读 ATT 只关心顺序和间隔，不关心绝对时刻）。
- payload 首字节是类型：

| 首字节 | 含义 | 说明 |
|---|---|---|
| `0x01` | HCI Command | 主机 → 控制器 |
| `0x02` | ACL Data | 承载 L2CAP/ATT，**业务数据在这里** |
| `0x04` | HCI Event | 控制器 → 主机（连接完成、加密变更等） |
| `0xfc` | 文本日志 | PacketLogger 自己的注释行 |

实测这份包（`private/captures/jk-2蓝牙包.pklg`，6746 字节）：

```
总记录 201 条
类型分布  HCI_CMD 70 / ACL 24 / HCI_EVT 27 / LOG 21 / 其他少量
捕获头  Product: iPhone8,4  Firmware: 19.1.144.603  Chipset: BCM_43452  Transport: UARTL
```

### 9.2 两处最常见的错误

```python
# ✗ 错 1：把 totalLen 当整条记录长度 → 从第二条开始全部错位
off += total

# ✓ 对：整条记录 = 4 + totalLen
off += 4 + total

# ✗ 错 2：把 8 字节时间戳当 double（CFAbsoluteTime）
ts = struct.unpack('<d', buf[4:12])[0]      # 会得到 2e-308 这种垃圾

# ✓ 对：int32 秒 + int32 小数（相对基准未确认，用相对值）
sec  = int.from_bytes(buf[4:8],  'little', signed=True)
frac = int.from_bytes(buf[8:12], 'little', signed=True)
```

### 9.3 解析器：`scripts/pklg_dump.py`

仓库里已有可运行的实现，核心 20 行：

```python
def records(path):
    raw = open(path, 'rb').read()
    off = 0
    while off + 12 <= len(raw):
        total = int.from_bytes(raw[off:off+4], 'little')
        end = off + 4 + total                 # 整条记录 = 4 + totalLen
        if total < 8 or end > len(raw):
            break
        sec  = int.from_bytes(raw[off+4:off+8],  'little', signed=True)
        frac = int.from_bytes(raw[off+8:off+12], 'little', signed=True)
        yield sec, frac, raw[off+12:end]
        off = end
```

## 10. 蓝牙抓包 III：L2CAP 重组与 ATT 判读

### 10.1 ACL 包头

```
byte 0-1: handle(12bit) | PB(2bit) | BC(2bit)
byte 2-3: data length (LE)
byte 4.. : data
```

`PB`（Packet_Boundary）决定怎么拼：

| PB | 含义 |
|---|---|
| `0b10` | 首片（First fragment of L2CAP PDU） |
| `0b01` | 续片（Continuing fragment） |
| `0b00` | 未分片的完整 L2CAP PDU |

**只有首片带 4 字节 L2CAP 头**。不重组就会看到「假 CID」和「假长度」。

### 10.2 L2CAP 头

```
byte 0-1: L2CAP 长度（后续 payload 长度）
byte 2-3: CID（LE）     0x0004 = ATT，0x0006 = SM（配对），0x0005 = LE 信令
```

### 10.3 重整（可运行）

```python
def reassemble(acl_fragments):
    """acl_fragments: [(handle, pb, data)] → [(cid, l2cap_payload)]"""
    out, buf, need, cid = [], bytearray(), 0, None
    for handle, pb, data in acl_fragments:
        if pb == 0b10 or pb == 0b00:
            if len(data) < 4:
                continue
            need = int.from_bytes(data[0:2], "little")
            cid = int.from_bytes(data[2:4], "little")
            buf = bytearray(data[4:])
            if len(buf) >= need:
                out.append((cid, bytes(buf[:need])))
                buf, need = bytearray(), 0
        elif pb == 0b01 and cid is not None:
            buf += data
            if len(buf) >= need:
                out.append((cid, bytes(buf[:need])))
                buf, need = bytearray(), 0
    return out
```

### 10.4 ATT 操作码

| Opcode | 名称 | 方向 |
|---|---|---|
| `0x10` | Read By Group Type Request | C→S |
| `0x11` | Read By Group Type Response | S→C |
| `0x08` | Read By Type Request | C→S |
| `0x09` | Read By Type Response | S→C |
| `0x0a` | Read Request | C→S |
| `0x0b` | Read Response | S→C |
| `0x12` | **Write Request（带响应）** | C→S |
| `0x13` | Write Response | S→C |
| `0x52` | Write Command（无响应） | C→S |
| `0x1b` | **Handle Value Notification** | S→C |
| `0x1d` | Handle Value Indication | S→C |
| `0x1e` | Handle Value Confirmation | C→S |

本项目抓到的全部关键写操作都是 **`0x12` Write Request**（带响应、逐段确认），不是 `0x52`。
重放时如果用了无响应写，设备可能丢段 —— 这是一个真实踩过的坑。

### 10.5 handle 怎么对上 UUID

日志里只有 handle（`0x0019`），没有 UUID。三种对法：

1. **从 GATT 发现过程推**：抓包里先有 `Read By Group Type`（服务）和 `Read By Type`（特征），
   响应里带 UUID 与 value handle，按顺序就能建表。
2. **直接枚举当前设备**（更快）：
   ```bash
   python3 ble/probe.py info            # 打印服务/特征/属性 + handle
   ```
3. **已知经验值**：`ffe1` 的 value handle 在本机型上是 `0x0019`，CCCD 是 `0x001a`。

### 10.6 CCCD：为什么先写 `01 00`

```
#6  Write Request handle=0x0009 len=2 02 00   ← 某个特征的 CCCD，开 notify
#9  Write Request handle=0x001a len=2 01 00   ← ffe1 的 CCCD，开 notify
```

不订阅通知，你能写但收不到设备回报（电压/电流/开关都拿不到）。

### 10.7 本项目真实序列（重组后 14 个 ATT PDU 的关键 5 条）

```
#6  Write Request  handle=0x0009  len=2   02 00
#9  Write Request  handle=0x001a  len=2   01 00                 ← 开通知
#10 Write Request  handle=0x0019  len=80  D1:2026,17:11,29:15,91:11,80:22,
                                          D6:32,85:05,85:00,91:11,149:58,
                                          336:Y,247:N,D13:Y      ← 明文配置串
#11 Write Request  handle=0x0019  len=80  {"rpcResponse":"6Njb1hvh967m5GIv1QEXMQ==:IrSbXEbi…
#12 Write Request  handle=0x0019  len=80  7Met4fniHoqypFTb1ib3wxSv6dKYMOhuNPM1swrcBn…
#13 Write Request  handle=0x0019  len=11  bblGHrTW+"}              ← 加密 RPC 收尾
```

由此得到三条硬结论：

1. 数据通道是 `0x0019`（`0000ffe1` 的 value handle）；
2. **每段 80 字节**，用 Write Request 逐段写；
3. **顺序不能反**：先明文配置串，再加密 RPC；只写前者设备只会回一句版本号。

### 10.9 把抓包变成可重放的 `frames.txt`

`ble/probe.py replay` 的格式（每行一帧）：

```
# 注释行以 # 开头
# sleep=0.5 指定这一帧之后的间隔（秒）
ascii:D1:2026,17:11,29:15,91:11,80:22,D6:32,85:05,85:00,91:11,149:58,336:Y,247:N,D13:Y
ascii:{"rpcResponse":"<IV>:<CT>"
ascii:<CT 续段 1>
ascii:<CT 续段 2>} # sleep=1
```

重放：

```bash

python3 ble/probe.py replay --file frames.txt --name B03-XXXX
```

注意：

- `ascii:` 前缀表示按文本写，`hex` 直接写字节；
- 密文 RPC 是**云端实时生成**的，重放旧的可能无效（有时效）；正确做法是每次从云端取现成的再拆段；
- 重放属于**写操作**，受 `MIN_WRITE_GAP` 节流约束（见第 19 节）。

### 10.10 判读抓包时的四个经验

1. **先看有没有 `0x02` ACL**。全是 `0x04` HCI Event 说明你抓的是连接事件流，业务数据没进来（手机没真正通信）。
2. **看到 `0x0019` 就该警觉**：这是业务通道，每多一条写就少一次设备的写入预算。
3. **80 字节不是巧合**：BLE 默认 ATT MTU 23（payload 20），协商后常见 185/247；App 固定按 80 切段说明它自己做了分片协议。
4. **设备主动断连 = 指令被执行了**。改错布尔字段后设备会回版本号再断开（BLE 栈重启），这不是故障，是生效信号。

### 11.2 怎么确认哪个包是目标

2. **看运行日志**：`applet/local/wx<appid>/usr/miniprogramLog/log1`，里面有完整页面跳转和 API 调用：

   （`scanCode:fail not supported` 是 Mac 微信不支持扫码，手机上正常。）
3. **看修改时间**：你刚打开过的那个包，mtime 就是那一刻。

### 11.3 wxapkg 容器结构

```
┌────────────────────────────────────────────────────────────┐
│ 0xBE │ ?? ?? ?? ?? │ idxLen(4,BE) │ bodyLen(4,BE) │ 0xED   │  ← 前 14 字节
├────────────────────────────────────────────────────────────┤
│ count(4,BE)                                                 │  ← offset 14
├────────────────────────────────────────────────────────────┤
│ 索引条目 × count：                                          │  ← offset 18 开始
│   nameLen(4,BE) │ name(nameLen) │ offset(4,BE) │ size(4,BE) │
├────────────────────────────────────────────────────────────┤
│ body（文件内容区，base = 18 + idxLen）                       │
└────────────────────────────────────────────────────────────┘
```

要点：

- 首字节固定 `0xBE`，`offset 13` 固定 `0xED`；
- `idxLen` 在 offset **5**，`bodyLen` 在 offset **9**，`count` 在 offset **14**；
- 索引区从 offset **18** 开始；
- 每个条目的 `offset` 是**相对 body 起点**的偏移。

`scripts/unpack.mjs` 里的实现（可直接对照）：

```js
const idxLen  = buf.readUInt32BE(5);
const bodyLen = buf.readUInt32BE(9);
const count   = buf.readUInt32BE(14);
const idxEnd  = 18 + idxLen;
const base    = idxEnd;              // body 起点
```

### 11.4 V1MMWX：混合加密（新版微信）

头部 6 字节是 `V1MMWX`，说明是加密包。**它不是整体 AES** —— 这是最常见的失败原因：

```
[6 字节 "V1MMWX"]
[前 1024 字节]  AES-256-CBC
                  key = PBKDF2-SHA1(appid, "saltiest", 1000, 32)
                  iv  = "the iv: 16 bytes"
                  autoPadding = false
[1024 字节之后] 逐字节 XOR
                  xorKey = appid 倒数第二个字符的 ASCII
```

为什么是「倒数第二个字符」：`appid` 形如 `wxXXXXXXXXXXXXXXXX`，倒数第二个字符是版本位/校验位，
微信用它做**每 appid 不同的弱混淆**。本项目那份包是 `6`（`0x36`）。

```js
const key    = crypto.pbkdf2Sync(appid, 'saltiest', 1000, 32, 'sha1');
const iv     = Buffer.from('the iv: 16 bytes', 'utf8');
const d      = crypto.createDecipheriv('aes-256-cbc', key, iv);
d.setAutoPadding(false);
const head   = Buffer.concat([d.update(body.subarray(0, 1024)), d.final()]);
const xorKey = appid.charCodeAt(appid.length - 2);
const tail   = Buffer.from(body.subarray(1024).map((b) => b ^ xorKey));
const out    = Buffer.concat([head, tail]);      // out[0] 必须是 0xBE
```

**校验点**：解密结果首字节不是 `0xBE` → `appid` 错了（最常见是拿了目录名以外的 appid，
或者包根本没加密却传了 `--appid`）。

### 11.5 第二层坑：索引区被插入垃圾字节

即使解密成功，索引里也可能**随机插入 `0x01` 垃圾字节**，专门干掉朴素解析器。

症状：包里有 79 个条目，你只解出 21 个。

正确做法是**带校验的贪心 + DP 回溯**：

```js
// 每个候选条目必须同时满足：
// 1) nameLen ∈ (0, 400]
// 2) p+12+nameLen 不越界
// 3) 名字首字符是 '/'（或合法文件名字符）
// 4) 名字整体是合法可打印路径
function nameAt(p) { /* 见 scripts/unpack.mjs */ }
```

`unpack.mjs` 的策略：

1. **贪心**：从 `idxStart` 逐字节走，能解析成条目就吃，不能就 `p++` 记一次垃圾；
2. **DP 兜底**：如果条目数不够 `count`，用 `reach(p, need)` 记忆化搜索判断「从 p 开始能否正好解出 need 条」，逐步降 need 找最大可解析集合。

```js
const reach = (p, need) => {
  if (need === 0) return true;
  if (p > idxEnd) return false;
  if (memo.has(`${p},${need}`)) return memo.get(`${p},${need}`);
  const r = nameAt(p);
  return (r && reach(r.next, need - 1)) || reach(p + 1, need);
};
```

### 11.7 三种包形态的自动识别

`unpack.mjs` 会自己判断：

| 形态 | 判据 | 处理 |
|---|---|---|
| 明文包 | 首字节 `0xBE` | 直接解析 |
| `V1MMWX` 加密包 | 前 6 字节 `V1MMWX` | 混合解密后再解析 |
| 头部带垃圾偏移 | 首 4096 字节里搜 `0xBE` 且其后第 13 字节为 `0xED` | 跳过前缀 |

```js
function findHeader(buf) {
  if (buf[0] === 0xbe) return 0;
  for (let i = 0; i < Math.min(buf.length - 20, 4096); i++)
    if (buf[i] === 0xbe && buf[i + 13] === 0xed) return i;
  return -1;
}
```

### 11.8 解包失败速查

| 现象 | 原因 | 处理 |
|---|---|---|
| `加密包需要 --appid` | 没传 appid | 传目录名里的 `wx...` |
| `AES 段解密后无 0xBE 魔数` | appid 错 / 包其实没加密 | 换 appid，或去掉 `--appid` 试明文解析 |
| 解开只剩 `__APP__` 一个文件 | 索引解析失败 | 看是否有 `跳过索引垃圾` 输出；确认用了本仓库的 DP 版本 |
| 只解出 21/79 | 用了几年前的开源工具 | 换 `scripts/unpack.mjs` |
| 中文文件名乱码 | 名字按 latin1 读 | 统一按 `utf8` 读 |
| 解出大量 0 字节文件 | `offset` 当绝对偏移算了 | `offset` 相对 body（`base = 18 + idxLen`） |

## 13. 小程序逆向 III：沙箱动态执行

静态读不到，就把小程序**跑起来**。

### 13.1 原理

`app-service.js` 是一个自执行包，内部用模块工厂 + `require` 组织代码。
只要提供一套假的全局环境，`Page({...})` / `App({...})` 就会真的注册，页面方法变成**可调用的真函数**。

`scripts/analyze.mjs` 提供的最小可用环境：

```js
const ctx = vm.createContext({
  console, setTimeout, clearTimeout, Promise, JSON,
  App: makeApp, Page: makePage, Component: () => {},
  getApp: () => app, getCurrentPages: () => pageInstances,
  wx: fakeWx,                       // ← 核心：记录所有调用
  __wxConfig: { ... },
});
vm.runInContext(code, ctx, { timeout: 15000, filename: 'app-service.js' });
```

`fakeWx` 里 `request` / `login` / `getStorageSync` / `scanCode` / `writeBLECharacteristicValue`
全部是记录器：

```js
request(opt) {
  const rec = { seq: ++seq, method: (opt.method || 'GET').toUpperCase(),
                url: opt.url, header: opt.header, data: opt.data ?? null };
  sandboxRecords.push(rec);
  opt.success?.({ statusCode: 200, data: { code: 0 } });   // 让它继续跑
}
```

关键细节：**必须用小程序自己的 `require` 驱动模块工厂**，否则 `Page()` 不会被执行。
`analyze.mjs` 的做法是先跑看起来像入口的模块（`pages/index/index`），让 `App/Page` 尽早注册。

### 13.2 跑

```bash
# 动态 + 静态一起
node scripts/analyze.mjs out/app-service.js

# 只静态（快，但拿不到签名实值）
node scripts/analyze.mjs out/app-service.js --static

# 指定入口模块（页面路径无效时）
node scripts/analyze.mjs out/app-service.js --entry "pages/ScanCode/ScanCode.js"

# 让沙箱里的业务流有可控输入
SANDBOX_ROOM=301 SANDBOX_QR=<二维码内容> node scripts/analyze.mjs out/app-service.js
```

### 13.3 输出怎么读

```
【抓到的实际请求】
  #3 POST https://dorm.example.com/api/dorm/power/recover
      header: {"Authorization":"Bearer ...","X-Sign":"e7addadc43a213171cf5bb5b55c0fc04"}
      body  : {"roomNo":"SANDBOX_ROOM","qrToken":"SANDBOX_QR_CONTENT","ts":1794708628536}

【BLE 调用序列（小程序自己就有蓝牙通道？）】
  {"api":"createBLEConnection","deviceId":"..."}
  {"api":"writeBLECharacteristicValue","value":"D1:2026,..."}

【签名/凭证相关标识】
  sign  MD5  signMod
```

三块信息各有用途：

| 区块 | 用途 |
|---|---|
| `calls` | 拿到 URL / header / body 的**真实结构**，直接对应 `private/config/config.json` 的 `api` 字段 |
| `header.X-Sign` | 拿到**签名实际输出值** → 用于验证你实现的签名算法（对拍） |
| `ble` | 判断指令到底走 HTTP 还是 BLE；本项目就是在这里确认「写走 BLE」 |

### 13.4 用签名实值反推算法

有了「输入参数 + 签名值」，签名算法就是可暴力验证的：

```bash
# 假设模板是 {sortedParams}&ts={ts}&k={secret}
node - <<'JS'
const crypto = require('node:crypto');
const params = { roomNo: '301', qrToken: 'ABC', ts: 1794708628536 };
const sorted = Object.keys(params).sort().map(k => `${k}=${params[k]}`).join('&');
for (const secret of ['DORM9f2c', 'xxx', 'FILL']) {
  const s = `${sorted}&ts=${params.ts}&k=${secret}`;
  console.log(secret, crypto.createHash('md5').update(s).digest('hex'));
}
JS
```

把它和抓到的 `X-Sign` 比对，命中即算法确认。这也是 `test/selftest.mjs` 里「签名算法对拍」那一节在做的事。

### 13.5 沙箱跑不起来怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| `【沙箱运行异常】` + 缺某个 API | 少了 `wx.*` 或 DOM | 在 `fakeWx` 里补桩，或改用抓包 |
| `calls` 为空 | 页面没被触发 | 换 `--entry`；或用 `SANDBOX_QR` 给输入 |
| 只注册了 App 没注册 Page | 入口模块猜错 | 从 `app-config.json` 的 `pages[0]` 拿真实入口 |
| 卡住不返回 | 有 `setInterval` / 死循环 | 靠 `vm` 的 `timeout: 15000` 兜底 |
| 报 `__TENCENT_CHAOS_VM is not a function` | VM 运行时缺失 | 把 VM 定义那段也放进 context（通常在文件头） |

## 14. 小程序逆向 IV：Chaos VM 与字符串表

### 14.1 长什么样

```js
var __TENCENT_CHAOS_VM = function () { /* ... 解释器 ... */ }();
__TENCENT_CHAOS_VM("QhQKCBISKhICDBIAEip0AiAgEnQgdBoCIhpuQG5ebuABbsIB...")
  (17181, [], { /* 辅助函数 */ },
   ["require", "Page", "deviceName", "powerRestoration", ...]);
```

- 第一串 base64 是**字节码**；
- 数字是寄存器/常量池规模；
- 最后一个数组是**明文标识符表**。

### 14.2 突破口 A：把 VM 跑起来

思路和上一节一样，只是要保证 VM 定义在 context 里、并且 `Page/App/wx` 都能用：

```js
const ctx = vm.createContext({ console, setTimeout, wx: fakeWx, Page: makePage, App: makeApp });
vm.runInContext(entireAppServiceJs, ctx, { timeout: 20000 });
// 之后 ctx 里的 pageInstances 就是真实注册的页面，方法可直接调用
```

本项目就是这么从 `pages/thingsboard_Install` 里跑出登录 / 读属性 / 写属性三个请求的。

### 14.3 突破口 B：直接读尾部的明文字符串表

压缩器为了 minify 必须**保留属性名**（否则 `this.xxx` 全废），于是这些名字以明文躺在数组里：

```js
__TENCENT_CHAOS_VM("...", false)(17181, [], {...},
  ["require","Page","deviceName","...","powerRestoration","..."]);
```

把它们抽出来 grep，等于拿到一份「方法名清单」：

```
request, method, header, username, password, Authorization, token
getSharedAttributeValue, updateSharedAttributeValue
CreateUpdateDevice, postDeviceUpdateTelemetry
TB_ElectricControlSwitch, TB_RoomStaticControlSwitch, TB_TimeControlSwitch
TB_TimerOn, TB_TimerOff, TB_CustomerName, TB_CustomerPassword
```

**这比硬啃字节码高效一个数量级。** 看到 `updateSharedAttributeValue` 就知道有「写云端属性」的能力，
看到 `TB_CustomerPassword` 就知道账号密码是从二维码/设置页来的。

### 14.4 顺手提取字符串表的小脚本

```bash
node - <<'JS'
const fs = require('node:fs');
const src = fs.readFileSync('out/app-service.js', 'utf8');
const out = new Set();
// 匹配所有形如 [ "a","b",... ] 的长数组
for (const m of src.matchAll(/\[((?:\s*"[^"\\]{1,40}"\s*,?){20,})\]/g)) {
  for (const s of m[1].matchAll(/"([^"\\]{1,40})"/g)) out.add(s[1]);
}
console.log([...out].filter(s => /^[A-Za-z_][\w.]{2,}$/.test(s)).sort().join('\n'));
JS
```

### 14.5 这套方法的天花板

| 能拿到 | 拿不到 |
|---|---|
| 页面路由、方法名、属性名 | 字节码里的具体常量（如加密密钥） |
| 请求 URL/header 结构（跑起来后） | 被 VM 内联的数值表 |
| 业务分支的大致形状 | 精确的浮点/布尔字段语义 |

所以最终结论要靠**三条证据交叉**：静态结构 + 沙箱调用 + 空口抓包。
本项目关于「控制走 BLE」的结论，就是解包（BLE API 序列）+ 抓包（没写请求）+ 空口（80 字节写帧）三方一致才定下来的。

## 15. 私有协议还原：高卫监控器的 BLE 协议

### 15.1 设备档案（实测）

```
产品    高卫智能用电监控器（型号 JK-2，下文简称 JK-2）
设备码  设备正面二维码下方的印刷编码（= 云端设备令牌，如 B03-<房间号>）
模块    DX-smart DX-BT24（BLE 串口透传）
固件    +VERSION=V2.1.0 / 应用固件 POWER02 B03.08
名称    B03-<房间号>            ← 设备名 = 设备令牌
地址    macOS 上是随机私有地址，每次扫描都变 → 按名字匹配
服务    0000ffe0-0000-1000-8000-00805f9b34fb   (Vendor specific)
特征    0000ffe1  read + write + notify + write-no-response   ← 数据通道（handle 0x0019）
        0000ffe2  write only
MTU     协商后可用；App 固定按 80 字节分段写
写入    Write Request（带响应，ATT opcode 0x12）
```

账号密码/令牌：**设备侧面二维码的内容就是 `B03-<房间号>`**（抓包埋点里能看到 `?bt_id=B03-xxxx`）。

### 15.2 两条云端指令

复电需要两条字符串，**都从云端实时取**（不能缓存、不能跨设备复用）：

```bash
# 1) 明文配置串（80B 左右，寄存器快照）
curl -s -X POST "$BASE/api/v1/$TOKEN/rpc" -H 'Content-Type: application/json' \
  -d '{"method":"getCurrentRPCStr","params":{"temperature":"25"}}'

# 2) 加密 RPC（171B 左右，真正的指令负载）
curl -s -X POST "$BASE/api/v1/$TOKEN/rpc" -H 'Content-Type: application/json' \
  -d '{"method":"getCurrentRPCStr_B03.08","params":{"temperature":"25"}}'
```

返回形态：

```
# getCurrentRPCStr（明文）
"D1:2026,23:11,29:15,97:10,87:57,D6:04,92:05,92:00,98:11,156:58,343:Y,254:N,D13:Y"

# getCurrentRPCStr_B03.08（密文，IV:CT 都是 base64）
"6Njb1hvh967m5GIv1QEXMQ==:IrSbXEbi…（共约 171 字节）"
```

`method` 名里的 `B03.08` 是**固件版本后缀**，会随固件变化（`RPC_getCurrentTimeStr_<版本>`）。

### 15.3 写入序列（顺序不能错）

```
① 明文配置串    → 分 N 段（每段 80B）Write Request (0x12) → handle 0x0019
② json of 加密RPC → {"rpcResponse":"<IV>:<CT>"} → 分 3 段（80/80/11）Write Request
```

抓包里的真实 5 条写：

```
#6  WR handle=0x0009 len=2   02 00                 ← CCCD，开通知
#9  WR handle=0x001a len=2   01 00                 ← ffe1 的 CCCD，开通知
#10 WR handle=0x0019 len=80  D1:2026,...           ← 明文配置串
#11 WR handle=0x0019 len=80  {"rpcResponse":"6Njb…" ← 加密 RPC 第 1 段
#12 WR handle=0x0019 len=80  7Met4fniHoqypFTb1ib3wxSv6dKYMOhuNPM1swrcBn…
#13 WR handle=0x0019 len=11  bblGHrTW+"}            ← 收尾
```

**只写 ① 没有用。** 设备会回一句 `fw_title:POWER02,fw_version:B03.08` 然后什么都不做。
这一条排查了很久：明文串只是「寄存器快照 + 时间参数」，真正的开关指令在 ② 里。

### 15.4 状态回报格式（设备 → 手机，走 notify）

```
1:B03-XXXX,2:20261115,3:112631,4:744.61,5:93.8,6:232.3,7:0.625,8:0.648,
9:0,10:0,11:0,12:0,13:2,14:0.3,15:0.266,16:0.004,17:1,
18:POWER02,19:B03.08,20:790,21:20261115,22:085448,23:0,
24:Y,25:N,26:Y,27:0500-1158,28:63,29:0,30:0
```

| 字段 | 含义 | 备注 |
|---|---|---|
| 1 | 设备名 | `B03-XXXX` |
| 2 / 3 | 日期 `YYYYMMDD` / 时间 `HHMMSS` | 设备本地时钟 |
| 4 | 累计电量 kWh | **故障时归零** |
| 5 | 待定（疑似剩余/功率相关） | 抓包间会漂移 |
| 6 | **电压 V** | **判断有没有电看这个**（>200V 且 7>0 才是真通电） |
| 7 | **电流 A** | |
| 8 | 功率因数 | |
| 9–12 | 各项即时值 | 多数为 0 |
| 13 | **状态码** | 0/2 正常；**24 = 监控器响应时钟异常** |
| 14–17 | 告警计数 / 参数 | |
| 18 / 19 | 固件名 / 版本 | `POWER02` / `B03.08` |
| 20 | 序号 | 故障时 0 |
| 21 / 22 | 上次事件日期 / 时间 | 故障时 `00000000` |
| 23 | 待定 | |
| **24 / 25 / 26** | **三个开关 Y/N** | **显示 Y 不代表有电** |
| **27** | **供电时段 `HHMM-HHMM`，12 小时制** | `0500-1158` = 05:00 ~ **23:58** |
| 28 | 待定（常见 63） | |
| 29 / 30 | 待定 | |

### 15.5 四个必须知道的坑

**坑 1：字段 27 是 12 小时制**

云端属性写 `TimerOneOff: "23:58"`，设备里存的是 `1158`。
看到 `1158` 不要以为是上午 11:58。

**坑 2：开关显示 Y 不等于有电**

故障态时 `24/25/26` 仍是 `Y/N/Y`，但电压电流全 0，继电器实际断开。
**唯一可信的判据是 `6`（电压）和 `7`（电流）。**

**坑 3：`temperature` 参数会让所有数字 key 整体平移**

```
temp= 5 → D1:2026,93:11,29:15,67:11,56:05,D6:25,61:05,61:00,67:11,125:58,312:Y,223:N,D13:Y
temp=35 → D1:2026,95:11,29:15,69:11,58:05,D6:27,63:05,63:00,69:11,127:58,314:Y,225:N,D13:Y
```

每 +10 度，key 全部 +1～2。所以配置串里的 key **不能当寄存器地址直读**，
必须减去 `f(temperature)` 的偏移。这也是「盲改布尔字段」风险高的原因。

**坑 4：改错布尔字段会让设备主动断连**

写入异常布尔值后：设备先回版本号，然后**主动断开 BLE**（BLE 栈重启）。
这是指令「被执行了」的信号，不是通信故障。重连后写回基线配置即可恢复。

### 15.6 探针工具（`ble/probe.py`）

写代码前先用它把设备摸清：

```bash
python3 ble/probe.py scan                     # 扫周边 BLE（-a 显示全部）
python3 ble/probe.py info                     # 枚举服务/特征/属性 + handle
python3 ble/probe.py listen --seconds 20      # 只收 notify，看设备自发回报
python3 ble/probe.py send --ascii "D1:2026,..."        # 按文本写一帧
python3 ble/probe.py send --hex 0103030000000944       # 按字节写一帧
python3 ble/probe.py send --hex 00 --no-response       # 无响应写（0x52）
python3 ble/probe.py replay --file frames.txt --interval 0.3
python3 ble/probe.py brute --start 0 --end 64          # Modbus 风格寄存器试探
```

**对照实验是还原协议最快的办法。** 本项目做过的：

| 写入内容 | 设备响应 | 结论 |
|---|---|---|
| 完整合法配置串 | `fw_title:POWER02,fw_version:B03.08` | 按行解析文本，格式对才应答 |
| 垃圾字节 `00 01 02 03` | 无 | 不是二进制协议 |
| 垃圾文本 `zzzz` | 无 | 需要合法字段结构 |
| 配置串前缀 `D1:2026,19:11` | 无 | 字段必须完整 |
| 空写 | 无 | — |
| 只写明文、不写加密 RPC | 只回版本号 | **指令在加密 RPC 里** |

### 15.7 还没解开的部分（诚实标注）

- 加密 RPC 的算法：形如 `<IV_b64>:<CT_b64>`，16B IV + 96B 密文，熵接近 8.0，是分组密码（AES/SM4 类）；
  **密钥在设备里**，目前不需要——每次从云端取现成的即可。
- 字段 5 / 9–12 / 23 / 28–30 的精确语义（不影响复电与读数）。
- 开关 24/25/26 与云端三个属性的精确一一对应（有一项疑似反相）。
- `300:Y,247:N,D13:Y` 这类布尔字段里，哪个才是「通电」位：盲试风险高，需要更多抓包样本。

> 复电不需要解开这些。**能复现就够了，理解可以慢慢补。**

## 16. 云端：ThingsBoard 设备 API 与 SHARED_SCOPE

### 16.1 怎么认出是 ThingsBoard

三条特征：

1. 端口 `8080`，路径 `/api/auth/login`、`/api/plugins/telemetry/...`；
2. 错误格式固定：
   ```json
   {"status":401,"message":"Invalid username or password","errorCode":10,"timestamp":1794711001899}
   ```
3. 遥测里是数字 key + 名称 key 混排（`1:...`、`7:TimerOneOn`），典型的「设备侧自定义 key 映射」。

### 16.2 设备令牌（无需登录，但只能读）

```
令牌 = 设备名 = B03-<房间号>
```

```bash
curl -s "$BASE/api/v1/$TOKEN/attributes" | python3 -m json.tool
```

真实返回：

```json
{
  "shared": {
    "ElectricControlSwitch":   "Y",
    "TimeControlSwitch":       "Y",
    "RoomStaticControlSwitch": "Y",
    "TimerOneOn":  "5:00",
    "TimerOneOff": "23:58",
    "Version":     "B03.01",
    "fw_title":    "POWER02",
    "fw_version":  "B03.09",
    "fw_size":     114780,
    "PassWordOfDetails": "<已脱敏>"
  }
}
```

能做的：

```bash
# 读全部共享属性
curl -s "$BASE/api/v1/$TOKEN/attributes"
# 只读指定 key（省流量）
curl -s "$BASE/api/v1/$TOKEN/attributes?sharedKeys=ElectricControlSwitch,TimerOneOff"
# 读实时配置串
curl -s -X POST "$BASE/api/v1/$TOKEN/rpc" -H 'Content-Type: application/json' \
     -d '{"method":"getCurrentRPCStr","params":{"temperature":"25"}}'
```

不能做的：**写 `shared` 属性**。`POST /api/v1/{token}/attributes` 只能写 client scope，
shared 的写权限在服务端（学校管理员）。

> `PassWordOfDetails: <已脱敏>` 是「详情页口令」，**不是 ThingsBoard 账号密码**，别拿去登后台。

### 16.3 令牌可枚举 = 部署缺陷

格式是 `B03-<房间号>`，`ble/jk2.py discover` 扫一圈就能看到同层十几台：

```
B03-XXXX（设备编号已脱敏）
```

也就是说**同楼任意房间的用电状态都能读**。这不是本仓库造成的，是部署方用「可推导的设备名」当访问令牌。
**唯一正确的用法：只读写自己那台。**

### 16.4 账号 JWT：唯一能真正远程控电的路

```http
POST /api/auth/login
{"username":"...","password":"..."}          → {"token":"<JWT>","refreshToken":"<RT>"}

POST /api/auth/token
{"refreshToken":"<RT>"}                      → 新 JWT

GET  /api/user/devices                       → 名下设备列表
GET  /api/plugins/telemetry/DEVICE/{id}/values/attributes/SHARED_SCOPE?keys=...
POST /api/plugins/telemetry/DEVICE/{id}/SHARED_SCOPE
{"ElectricControlSwitch":"Y","RoomStaticControlSwitch":"N","TimeControlSwitch":"N"}
```

账号密码从哪来：

1. **安装时扫的那张二维码**（宿管/学校发的），内容里就是 `TB_CustomerName` / `TB_CustomerPassword`；
2. 小程序「设置」页可手填；
3. 本地 `MMKV` 缓存（加密，需要 hook）。

### 16.5 三层断电机制 —— 「一劳永逸」的正确姿势

```
① TimeControlSwitch       + TimerOneOn/Off   → 每天到点断电
② RoomStaticControlSwitch                    → 长时间无人用电后断电
③ ElectricControlSwitch                      → 总开关
```

每天扫码复电只动了 ③，所以第二天还会断。把 ① ② 关掉：

```json
{"ElectricControlSwitch":"Y","RoomStaticControlSwitch":"N","TimeControlSwitch":"N"}
```

```bash
node client/tb.mjs forever --device 301
```

`forever` 的流程是「读 → 写 → 读回校验」：

```
修改前: {"ElectricControlSwitch":"N","RoomStaticControlSwitch":"Y","TimeControlSwitch":"Y"}
已关闭自动断电机制
修改后: {"ElectricControlSwitch":"Y","RoomStaticControlSwitch":"N","TimeControlSwitch":"N"}
```

**读回还是 `Y`** → 服务端有策略强制覆盖（学校锁定），那就退回「定时复电 / BLE 复电」。

### 16.6 遥测字段映射

`POST /api/v1/DeviceUpdate/telemetry` 里能看出整套 key：

```
1:DeviceUpdate   7:TimerOneOn   8:TimerOneOff
9:ElectricControlSwitch   10:RoomStaticControlSwitch   11:TimeControlSwitch
12~27: 各项用电参数（对应 BLE 回报里的 4/5/6/7/8 等）
```

## 17. 客户端实现：recover.mjs 的签名、token、幂等

这个是「HTTP 复电」路线的核心（适用于有 `/api/.../recover` 接口的校园平台）。
如果你那套系统是 ThingsBoard，用第 16 节就够了；两条路可以并存。

### 17.1 配置文件全字段

```jsonc
{
  "baseUrl": "https://dorm.example.com",
  "appid": "wxXXXXXXXXXXXXXXXX",
  "roomNo": "301",

  "sign": {
    "type": "md5",                                  // md5 | hmac-sha256 | none
    "template": "{sortedParams}&ts={ts}&k={secret}", // 可用变量见下
    "secret": "FILL_FROM_REVERSED_JS",
    "placement": "header",                          // header | query | body
    "headerName": "X-Sign",
    "paramName": "sign",
    "sendTs": true,
    "sendNonce": false
  },

  "headers": {
    "content-type": "application/json",
    "user-agent": "Mozilla/5.0 (iPhone; ...) MicroMessenger/8.0.49",
    "Referer": "https://servicewechat.com/{appid}/0/page-frame.html"
  },

  "api": {
    "login":    "/api/dorm/auth/login",
    "roomInfo": "/api/dorm/room/info",
    "recover":  "/api/dorm/power/recover"
  },

  "okCode": 0,
  "verify": { "enabled": true, "retries": 8, "intervalMs": 1500 },
  "retry":  { "times": 3, "backoffMs": 800 },
  "jitterMs": 1200,
  "timeoutMs": 10000
}
```

**签名模板可用变量**：

| 变量 | 含义 |
|---|---|
| `{sortedParams}` | 参与签名的参数按 key 升序拼成 `k=v&k=v` |
| `{ts}` | 毫秒时间戳（`sendTs` 控制是否放进请求） |
| `{nonce}` | 随机串（`sendNonce`） |
| `{secret}` | `sign.secret` |
| `{appid}` | `appid` |
| `{token}` | 当前登录 token |
| `{body}` | 原始请求体字符串 |

三种常见算法：

```jsonc
// 1) 全参数排序 md5（最常见）
{ "type": "md5", "template": "{sortedParams}&ts={ts}&k={secret}" }

// 2) HMAC-SHA256
{ "type": "hmac-sha256", "template": "{sortedParams}&ts={ts}", "secret": "..." }

// 3) 无签名，纯 token
{ "type": "none" }
```

### 17.2 一次复电的完整流程

```
1) POST api.login      {qrToken?, roomNo}          → token + ttl
   （有缓存 token 且未过期则跳过）
2) GET  api.roomInfo   ?roomNo=301&ts=...          → power: true/false
   ├─ power == true  → 幂等跳过（除非 --force）
   └─ power == false → 继续
3) POST api.recover    {roomNo, qrToken?, ts}      → code == okCode
4) 轮询 api.roomInfo   verify.retries 次             → 等到 power == true
```

任何一步返回 401 / 业务失效码 → 清空 token 重新走 1)。

### 17.3 token 生命周期

- 缓存文件：`private/state/.state.json`（`STATE_PATH` 可覆盖），权限 `0600`；
- 结构：`{ "token": "...", "expiresAt": 1794720699704, "refreshToken": "..." }`；
- 复用条件：`Date.now() < expiresAt - 60000`（提前 1 分钟刷新）；
- 失效时自动重登一次，仍失败则抛错并保留原 token 供排查。

如果服务端的 `wx.login` code 换 token 与 openid 强绑定（换机器就拿不到），
把抓到的长期 token 写进 `refreshToken` 字段兜底。

### 17.4 幂等、重试、抖动

| 机制 | 实现 | 为什么需要 |
|---|---|---|
| 幂等 | 先读 `roomInfo.power`，已通电就跳过 | 避免把设备当开关按 |
| 重试 | `retry.times` × `backoffMs` 指数退避 | 校园网 4G 抖动 |
| 抖动 | `jitterMs` 在请求前随机等待 | 避免每天同一秒打接口，行为太像脚本 |
| 校验 | `verify` 轮询确认 `power=true` | 「接口返回成功」≠「真的来电」 |

### 17.5 CLI

```bash
node client/recover.mjs --room 301              # 正常执行
node client/recover.mjs --room 301 --dry-run    # 只打印将要发的请求与签名，不发网络
node client/recover.mjs --room 301 --check      # 只查状态
node client/recover.mjs --room 301 --qr-token X # 指定二维码票据
node client/recover.mjs --room 301 --force      # 已通电也再发一次（调试用）
node client/recover.mjs --once                  # 单次执行（给 launchd 用）
```

日志同时写 stdout 和 `private/logs/recover.log`。

### 17.6 mock 服务端的行为（用来校验你的实现）

`mock/server.mjs` 不是「永远返回 200」的假服务，它会真校验：

| 行为 | 说明 |
|---|---|
| 签名校验 | 错 `X-Sign` → 403 + 业务码 |
| token 过期 | 401，逼客户端重登 |
| 幂等 | 已通电再复电 → `code != 0` 提示已通电 |
| 二维码一次性 | 同一票据第二次 → `code 1002`；房间不匹配 → `1003`；过期 → `1004` |
| 抖动 | 可配延迟，验证客户端 timeout/retry |

初始房间：`301` 断电、`302` 通电、`303` 断电。

## 18. 部署与自动化

### 18.1 launchd（macOS 正统做法）

不要在 launchd 里手写 plist，用模板渲染：模板里的 `__PROJECT_DIR__`、`__DEV_TOKEN__`、`__PYTHON__`
会被替换成真实值，产物落在 `private/launchd/`（不进仓库）。

```bash
# 每天 06:00 / 22:00 各复电一次（推荐：最省、最安全）
./run.sh install-daily

# 常驻守护（KeepAlive，崩了自动拉起；写包多，见第 19 节）
./run.sh install

# 查看 / 卸载
launchctl list | grep -E "jk2|dorm"
tail -f private/logs/jk2.log
./run.sh uninstall-daily
./run.sh uninstall
```

自己看看渲染结果：

```bash
cat private/launchd/com.dorm.jk2-daily.plist
plutil -lint private/launchd/com.dorm.jk2-daily.plist
```

要点：

- plist 里的 `EnvironmentVariables` 会带 `PRIVATE_DIR`，保证后台进程也能找到私有配置；
- `StandardOutPath` / `StandardErrorPath` 指向 `private/logs/`；
- **后台进程需要蓝牙权限**：系统设置 → 隐私与安全性 → 蓝牙，勾选「终端」和你安装的 `python3`；
- 睡眠会暂停定时任务，`launchd` 在唤醒后会补跑（`StartCalendarInterval` 的语义）。

### 18.2 内置调度器（比 launchd 灵活）

```bash
python3 schedule/runner.py add --at 07:00 --room 301                # 每天 07:00
python3 schedule/runner.py add --at 07:00 --cron weekday --jitter 600
python3 schedule/runner.py list
python3 schedule/runner.py remove 1
python3 schedule/runner.py run-once 1                                # 立刻跑某条
python3 schedule/runner.py daemon                                     # 前台常驻
```

- `--cron weekday` 只在周一到周五；
- `--jitter 600`：07:00 之后随机 0~600 秒内执行，避免每天同一秒；
- 任务表存在 `private/schedule/tasks.json`（含房间号，属于私有数据）。

### 18.3 BLE 触发：人到了才干活

```bash
./run.sh ble                                  # 扫周边 BLE（先确认能看到你的手机/手环）
./run.sh presence "iPhone" -65                # 你的设备 RSSI > -65 → 触发一次
./run.sh beacon <UUID>                        # 门口贴 iBeacon，进门即触发
python3 ble/trigger.py button --address <MAC> # BLE 按键当实体开关
python3 ble/trigger.py list-services --address <MAC>
python3 ble/trigger.py gatt --address <MAC> --char <UUID> --payload 01   # 直连写 GATT
```

- 内置 **90 秒节流**（`TRIGGER_COOLDOWN` 可调），走动不会反复触发；
- Apple 设备的 BLE 地址是随机私有地址，**按名字匹配**比按地址稳；
- `gatt` 模式是「如果电控本身就是 BLE 设备，绕开服务器直接写」的通用后门。

## 19. 写入预算与故障码 24

**这是本项目唯一一个会造成真实后果的地方，请读完再动手。**

### 19.1 一次复电 = 4 个 BLE 写包

```
配置串 1 包 + 加密 RPC 3 包 = 4 次 Write Request
```

### 19.2 写入预算

| 方式 | 每天写包 |
|---|---|
| 手动扫一次码 | 4 |
| 定点一天 2 次 | **8** |
| `watch` 每 600 秒 | 576 |
| `watch` 每 60 秒 | 5760 |

**设备的设计负载是「人走到跟前，扫一次码」，一天几次。**
任何常驻轮询都先问自己：这个写包量合理吗？

### 19.3 故障码 24：监控器响应时钟异常

APP 弹窗原文：

> 本次扫码复电结束。扫码前监控器状态：**24-监控器响应时钟异常**，30分钟后重试

对应状态回报 `13:24`（正常是 `0` 或 `2`）。症状：

| 字段 | 正常 | 故障 |
|---|---|---|
| 6 电压 | 231.8 V | **0** |
| 7 电流 | 0.483 A | **0** |
| 4 累计电量 | 599.90 | **0** |
| 18/19 固件 | POWER02/B03.08 | **0/0** |
| 20 序号 | 1486 | **0** |
| 21/22 上次事件 | 20261115/004154 | **00000000** |
| 13 状态码 | 2 | **24** |
| 24/25/26 开关 | Y/N/Y | Y/N/Y（**不变，容易误判**） |

**继电器锁死在断开状态**，所以房间没电；但小程序仍显示「开关=开」。

恢复（软件无法修复）：

1. **拔掉监控器电源，等 10 秒再插上**（最快，RTC 重新初始化）；
2. 等 30 分钟让设备自行退出保护态。

成因：**可能**与写入过频有关（配置串含时间字段 `D1:2026` 等，反复写入可能扰动 RTC），
**但未证实** —— 也可能是 RTC 电池或掉电。措辞上不要写成「就是写坏的」。

### 19.4 已内置的护栏

| 护栏 | 位置 | 说明 |
|---|---|---|
| `MIN_WRITE_GAP`（默认 600s） | `ble/jk2.py` | 同一设备两次写入的最小间隔，**落盘 `private/devices/.lastwrite.json`，跨进程生效** |
| `JK2_MIN_WRITE_GAP` | 环境变量 | 需要调试时才调，别为了「方便」调小 |
| `watch --interval` 默认 600 | `ble/jk2.py` | 从 60 秒改成 600 秒 |
| 风险提示 + 输入 `yes` | `jk2.py watch` / `启动守护.command` / `wait_power.py` | 非交互（launchd）时不阻塞，但提示照样写日志 |
| `--yes` / `--quiet-start` | `jk2.py` | 只跳过「询问」，不跳过「提示打印」 |

> 历史教训：第一版节流用进程内 `dict`，命令行每次都是新进程 → 节流形同虚设。落盘才有效。

### 19.5 正确用法建议

| 场景 | 建议 |
|---|---|
| 日常复电 | `./run.sh jk-recover` 手动点，或 `install-daily` 一天 2 次 |
| 看状态 | `jk-status` 会写设备，默认至少间隔 600 秒 |
| 守护模式 | `--interval 600` 起步，别更小 |
| 频繁调试 | **别干**，会写坏设备 |

## 20. 排错手册

### 20.1 HTTP / 抓包

| 症状 | 原因 | 处理 |
|---|---|---|
| 手机没网 | 代理地址/端口错、Mac 防火墙 | 换 `en1`、临时关防火墙 |
| `mitm.it` 打不开 | 没连同一 WiFi 或代理没生效 | 检查 WiFi 代理设置 |
| 全是证书错误 | 只装描述文件没开信任 | 设置 → 通用 → 关于本机 → 证书信任设置 |
| 小程序白屏 | SSL Pinning | 第 7 节 frida 绕过；或改走解包路由 |
| 抓不到写请求 | 写动作走 BLE，不走 HTTP | 第 8 节蓝牙抓包 |
| body 乱码 | gzip/br 或二进制 | 用 mitmproxy 界面看，或 `--set http2=false` |
| `suggested-config.json` 缺 secret | 签名密钥不在流量里 | 从解包 JS 里搜（第 12/13 节） |

### 20.2 BLE

| 症状 | 原因 | 处理 |
|---|---|---|
| 扫描列表为空 | 没给蓝牙权限 | 系统设置 → 隐私与安全性 → 蓝牙 |
| 扫不到设备 | 距离远 / 手机占用 | 靠近；把手机微信退出（BLE 被手机连着时 Mac 连不上） |
| 连上了但读不到数据 | 没订阅通知 | 先写 CCCD `01 00`，再 `start_notify` |
| 只回版本号，不复电 | 只写了明文配置串 | 必须再写加密 RPC（第 15.3 节） |
| 写一半失败 | 用了无响应写 | 改 Write Request（0x12），每段 80B 逐段确认 |
| 设备主动断连 | 指令生效（BLE 栈重启） | 正常，重连即可 |
| 电压电流全 0 | 可能进了故障码 24 | 拔电 10 秒重插（第 19.3 节） |
| 读 `ffe1` 拿到的是刚写的内容 | 该特征读回来是回显 | 看 notify，不要看 read |
| 地址每次都不一样 | macOS 随机私有地址 | 按名字匹配 |

### 20.3 解包 / 逆向

| 症状 | 原因 | 处理 |
|---|---|---|
| `加密包需要 --appid` | 没传 appid | 取目录名里的 `wx...` |
| `解密结果无 0xBE` | appid 错 | 核对 appid；或去掉 `--appid` 试明文 |
| 只解出少量文件 | 索引垃圾字节 | 用本仓库 DP 版解析器 |
| 沙箱 `calls` 为空 | 入口模块没触发 | `--entry` / `SANDBOX_QR`；或直接抓包 |
| `__TENCENT_CHAOS_VM` 报错 | VM 定义没进 context | 整文件一起 `runInContext` |
| grep `wx.request` 为 0 | 代码在字节码里 | 别下结论，跑沙箱或抓包 |

### 20.4 launchd / 定时

| 症状 | 原因 | 处理 |
|---|---|---|
| `launchctl list` 里没有 | plist 没 load / 渲染失败 | `./run.sh install-daily` 看输出；`plutil -lint` |
| 日志里报扫描失败 | 后台进程没蓝牙权限 | 隐私与安全性 → 蓝牙 → 加终端/python3 |
| 时间不准 | Mac 睡眠 | 唤醒后 launchd 会补跑；或关自动睡眠 |
| `render_plist` 报缺 DEV_TOKEN | `private/local.env` 没填 | 填 `DEV_TOKEN="B03-XXXX"` |

### 20.5 多宿舍

| 症状 | 原因 | 处理 |
|---|---|---|
| 某台一直连不上 | RSSI 太差 / 被手机占用 | `jk-discover` 看 RSSI；退出手机微信 |
| 批量操作很慢 | 串行轮询固有成本 | 接受，或减少设备数 |
| 状态显示 Y 但没电 | 字段 24/25/26 不可信 | 看电压/电流 |

### 22.4 术语

| 术语 | 含义 |
|---|---|
| **wxapkg** | 微信小程序包格式（`0xBE` 头 + 索引 + body） |
| **V1MMWX** | 微信 4.x 的包加密格式（AES 前 1024B + XOR 尾部） |
| **Chaos VM** | 腾讯的 JS 字节码虚拟机，小程序混淆产物 |
| **pklg** | Apple PacketLogger 的 HCI 日志格式 |
| **btsnoop** | 通用 HCI 日志格式（Android/Wireshark） |
| **ACL** | HCI 上的数据包类型，承载 L2CAP/ATT |
| **ATT** | BLE 属性协议（Read/Write/Notify） |
| **CCCD** | 客户端特征配置描述符，写 `01 00` 开通知 |
| **pklg / ATT handle** | 特征值地址，如 `0x0019` = `ffe1` 的 value |
| **ThingsBoard** | 开源 IoT 平台，本项目后端 |
| **SHARED_SCOPE** | ThingsBoard 的服务端共享属性作用域（唯一能远程控电的写入口） |
| **JWT** | 账号登录后的 Bearer Token |
| **设备令牌** | `/api/v1/{token}/...`，与设备名相同，只能读 |
