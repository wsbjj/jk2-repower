# 故障码 24：监控器响应时钟异常

## 是什么

APP 弹窗原文：

> 本次扫码复电结束。
> 扫码前监控器状态：
> **24-监控器响应时钟异常**，
> 30分钟后重试

对应设备状态回报里的 `13:24`。**字段 13 就是状态码**，正常值是小数字（0 或 2）。

## 表现

| 字段 | 正常 | 故障时 |
|---|---|---|
| 6 电压 | 231.8 V | **0** |
| 7 电流 | 0.483 A | **0** |
| 4 累计电量 | 599.90 | **0** |
| 18/19 固件 | POWER02/B03.08 | **0/0** |
| 20 序号 | 1486 | **0** |
| 21/22 上次事件 | 20261115/004154 | **00000000** |
| 13 状态码 | 2 | **24** |
| 24/25/26 开关 | Y/N/Y | Y/N/Y（不变） |

**继电器锁死在断开状态**，所以房间没电。
但开关逻辑还显示"开"，容易误判。

## 为什么会触发

设备 RTC（实时时钟）跟主控对不上，进入保护。

最可能的原因：**写入配置串太频繁**。

- 小程序的正常节奏是「扫一次码 → 写一次」
- 我们的 `watch` 模式原本每 60 秒写一次，一小时内写了几十次
- 而且每次从云端取的配置串数值都在漂移（`temperature` 参数影响），
  等于反复喂给设备不一致的时钟参数

配置串里 `D1:2026` 这类字段和日期时间相关，被反复改写就乱了。

## 怎么恢复

**① 物理断电（最快）**

拔掉 JK-2 电源，**等 10 秒**再插上。RTC 重新初始化，故障码清除。

**② 等 30 分钟**

APP 自己给的提示。设备会自行退出保护态，然后再扫码。

**③ 恢复后确认**

```bash
./run.sh jk-status
```

看到电压回到 230 左右、状态码变成 0 或 2 就正常了。

## 已经做的防护

工具里加了**写入节流**，防止再把设备写坏：

```python
MIN_WRITE_GAP = 120   # 秒，同一台设备两次写入的最小间隔
```

- 记录在 `ble/.lastwrite.json`
- 跨进程生效（命令行连续调用也会被拦）
- 可用环境变量 `JK2_MIN_WRITE_GAP` 调整

`watch` 默认间隔也从 60 秒改成了 **600 秒**。

## 正确用法建议

| 场景 | 建议 |
|---|---|
| 日常复电 | 手动点一次 `jk-recover`，别常驻 |
| 想看状态 | `jk-status`，但间隔 ≥ 2 分钟 |
| 守护模式 | 间隔设 600 秒以上 |
| 频繁调试 | **别干**，会写坏 |

说到底：**这设备不是给你高频轮询的**。
它的设计是「人走到跟前，扫一次码」。

## 未解开的

- 状态码完整的对照表（只确认了 24）
- 设备时钟是怎么同步的（云端 `getCurrentRPCStr` 里应该含时间，
  但具体哪个字段对应什么还没定）

### 覆盖的入口

| 入口 | 提示方式 |
|---|---|
| `python3 ble/jk2.py watch` | 方框提示 + 输入 yes 确认 |
| `./run.sh jk-watch` | 同上 |
| `启动守护.command` | shell 版提示 + 输入 yes |
| `ble/wait_power.py` | 方框提示（打印后直接跑） |
| `jk2.html` 守护按钮 | 浏览器 confirm 弹窗 |

### 后台/自动化场景

如果确实要跑后台（launchd），用 `--quiet-start` 跳过交互，
但**提示内容仍会写进日志**，事后可查：

```bash
python3 ble/jk2.py watch --interval 600 --yes
```

`--yes` 只跳过询问，不跳过提示打印。
